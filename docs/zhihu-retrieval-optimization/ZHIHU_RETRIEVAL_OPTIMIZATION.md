# 知乎 M2 检索优化方案：从“相关资料”到“能回答问题的证据”

版本：提案 v1.0｜日期：2026-09-12｜执行范围：`packages/zhihu` 为主。

## 1. 目标与边界

目标不是每次返回更多卡，而是在固定搜索与编译预算下，让前几张卡更直接回答研究问题，减少工具宣传和重复观点，同时保留来源与不确定性。

用户已经在 Windows 完成真实 Provider 和真实 HTTP 单请求联调。这证明 `ResearchRequest → EvidencePack` 可以运行，不证明证据已经足以构成 Roadmap，也不证明检索质量最优。[C2]

本轮只优化 M2，不接手多请求 Controller、RouteCandidate 综合、正式 BaselineProposal、前端、Plan Engine 或 History。保留 `pipeline`、Server Provider、`adaptZhihuCompilerOutput`、现有输入输出 schema。不要混用“任务相关”“引文存在”“事实已核实”三种判断。

本方案分为两个可独立验收的阶段：
- **阶段 A，建议现在执行：** 固定评测集、改善 Query 互补性、保留片段变体、按多列表名次融合、按问题类型排序、降低结果冗余。没有新增模型调用，仍复用现有 compiler。
- **阶段 B，后续可选：** 对少量候选做一次 LLM 语义重排。默认不实施；只有 A 的质量报告指出仍有明确缺口，且用户同意扩展时再做。

不采用的首轮方案：增加向量数据库、引入一套 RAG 框架、训练专用模型、每个片段多轮反思、多次自动补搜、绕过知乎授权抓全文。它们都会扩展本轮的接口与运维范围，却不能替代质量评测。

## 2. 对现有代码的诊断

下面都是对用户上传快照的观察，不代表远程仓库最新版本。[C1]

| 观察 | 具体位置 | 应对方向 |
|---|---|---|
| 已经有确定性 ranker，也已经使用 LLM 编译证据 | `ranker.py`、`evidence_compiler.py` | 不是从零增加“智能筛选”；补上薄弱环节 |
| `specificity_score` 的大量词表是 API、JSON、Python 等编码术语 | `ranker.py`，A4/A5 | 评分应按“方法/检验/风险/资源”等问题需求，而非单一职业词表 |
| 词面相关性只有英文词与中文二元组 | `relevance_score()` | 不假装它有语义理解；先利用多 Query 名次与任务线索 |
| 多 Query 的同一 source 只选第一次出现的 snippet 交给 compiler | `research_runner.py`，A2/A11 | 保留各次原始变体，挑最贴近问题的一份原文，不拼接 |
| source 的 Query 出现记录已存在，但没有利用每个结果列表中的名次融合 | `dep.trace`、`candidates` | 记录 queryIndex/resultRank，用 RRF 辅助排序 |
| 收到足够卡就停止编译，顺序影响最终输出 | `research_runner.py`，A3 | 优先编译直接回答问题、且能补充新信息的 source |
| 原 compiler 提示词已经要求“方法题不能用资源介绍凑数” | `evidence_compiler.py`，A7 | 不能把“再写一条相同提示词”当作完整优化；必须加入反例和真实输出评审 |
| 现有 `limit_per_author()` 用 `author_signature` 分组 | `deduplicator.py`，A6 | 本轮不要在 live runner 中调用它：签名字段未证明是唯一作者 ID |
| Node 校验严格要求 source_scope、版本、字段、风险标签 | `zhihu-boundary.ts`，A12 | 不随意新增卡片字段、改变 source_scope 或删除风险标记 |

四个合成短文本的实际旧 ranker 检查见 `snapshot_probe_results.json`：纯编码术语列表得到较高 specificity，木桌检查步骤得不到该项分数。这只揭示启发式的领域倾向，不能拿来声称某个真实排序一定错了。[C3]

## 3. 先明确“什么证据算好”

你的两张 live 卡中，第一张提供“固定决策、记录行为、做断言”的方法；第二张主要介绍一个工具，附带“流行”“五分钟上手”等作者说法。对“怎样编写基本测试”的问题，二者的用途不同。

建议以**问题需求**区分：

| 研究需要 | 优先找什么 | 不能直接等同于回答 |
|---|---|---|
| method 方法 | 明确动作及对象、步骤、输入与输出 | “有一个教程/有一个工具” |
| verification 检验 | 对照、检查办法、可观察失败、完成标准 | “很专业/效果很好” |
| risk 风险 | 触发条件、限制、失败方式、反例 | 不带条件的悲观或乐观结论 |
| experience 经历 | 做过什么、在什么背景、遇到什么结果 | 只有“我整理了一个资源” |
| concept 概念 | 定义、组成、区别 | 术语堆砌 |
| resource 资源 | 资源名称、适用范围、限制 | 未验证的“首选”“最流行”成为产品背书 |

第二张并非永远“垃圾”：在资源选择题中可以有用，在方法题中可能只是参考线索。不能针对某一个框架名字建立黑名单；也不能把知乎用户的否定观点、短回答、低赞回答一律剔除。

## 4. Query 优化：不扩大调用次数，先提高互补性

保留现有 Baseline `3 个问题 × 每题 2 条 Query` 的格式、澄清逻辑和单次 Planner 调用限制。通用 Planner 仍是“上限”，不得都改为强制 3 题。[C1 A10]

每题的两条 Query 不应只是换一个近义词后照搬；建议优先：

- Query A：主题 + 具体动作或对象。
- Query B：相同研究焦点的检验、失败、限制或另一种自然表述。

例如“初学者怎样检查 Agent 行为符合预期”：

```text
Agent 工具调用 测试 固定输出 断言
智能体 行为验证 调试 失败案例
```

这是 Query 设计示例，不是保证能搜到更好答案的固定模板。资源题可以使用“资源/入门资料/示例”，概念题不必硬塞“踩坑”。保留主题，避免为了多样性偏离原题。

不要把所有用户背景塞进 Query，不暴露姓名、联系方式、私人标识。时间/预算只有与研究焦点直接相关时才进入搜索词。不要预先认定某工具最好，也不要为了迎合某种立场只搜支持它的内容。

**执行器只执行 `request.searchQueries`。** 排序发现证据不足时，写入 `unresolvedQuestions` 或本地质量报告；自动改写或补搜属于下一轮 Controller，不在当前单请求中偷偷增加。

## 5. 候选池：去重 source，不丢掉 snippet 变体

同一篇文章可能在不同 Query 下返回不同片段。当前“保留第一份”的规则有利于确定性，但可能把更能回答问题的后续片段丢掉。[C1 A2]

建议的数据层次：

```text
source_id = zhihu:{content_type}:{content_id}
    ├─ variant A：原始 ZhihuResult、snippet hash、检索时间、出现位置
    └─ variant B：原始 ZhihuResult、snippet hash、检索时间、出现位置
```

每个 occurrence 记录 `query_index`、`result_rank`（从 1 开始）以及实际检索时间。一个 Query 中重复出现同一 source，RRF 只记最好的一个名次，不多次加分。

阶段 A 每个 source 仍最多编译一次。选择该 source 内**评分最高的一份完整原始 variant**，并使用该 variant 对应的 URL、作者、时间与正文。评分相同按 query_index、result_rank、hash 稳定打破平局。

绝对不能把 A、B 拼成“完整文章”，也不能清洗正文后把清洗后的文本作为原文。用于排序的清洗视图与 compiler 的原文必须隔离。source ID 不同但 URL 相似，不能擅自认定是同一篇并合并；问答中的不同 answer 必须保留。

目前 raw schema 没有经核实的稳定作者 ID。不要把作者签名、同名、匿名用户合并成一个作者，也不要把“不同 URL 数量”解释为“独立来源数量”。

## 6. 融合与排序：规则负责约束，compiler 负责主张

### 6.1 RRF：使用各 Query 的检索名次

为 source s 计算：

```text
RRF(s) = Σ 1 / (60 + best_rank_of_s_in_query_q)
```

只对实际出现的 Query 求和；未出现贡献 0。为了和其他 0–1 特征相加，本方案用 `successful_query_count / 61` 作分母归一化。空但成功的搜索也是 successful Query；全部失败沿用现有失败逻辑。

RRF 是融合结果列表的一种方法，不需要假设不同 Query 的原始 RankingScore 可以直接比较。这里把它用在同一 Provider 的多 Query 上，是待验证的工程应用，不是知乎相关性或事实可靠性的保证。[R1][R2]

### 6.2 任务感知的透明分数

保留旧 `rank_results()`，新增可回退的 profile。阶段 A 的建议初始权重是：

```text
priority = (
    0.45 * lexical_relevance
  + 0.20 * normalized_rrf
  + 0.25 * intent_surface_signal
  + 0.05 * recency_signal
  + 0.05 * engagement_signal
) * (1 - 0.50 * promotion_signal)
```

这些权重是**实验起点**，不是科学测出的概率。不要显示成“可信度 87%”。

`lexical_relevance` 使用研究问题为主、原 Query 为辅（0.8 × question overlap + 0.2 × max query overlap）。不要求每篇材料命中每项个人条件；基础不明不能推断“不适合初学者”。

`intent_surface_signal` 只识别可观察文字线索：动作+对象、对照+标准、条件+后果等。术语列表与数字个数不直接等于具体性。没有明确 intent 时给中性值，不强行推断。

`recency_signal` 默认中性；只有请求真的提出时效需要时，才使用已有编辑时间启发式。编辑时间不是事实核实时间，不认识的 freshness 文本不得变成“已满足最近一年”。保留当前 `freshness_not_enforced`。

推广信号只影响排序，不按“课程”“微信”等单个词硬删，不删除警示广告的原文。继续复用旧版保守清洗和推广逻辑。

### 6.3 多样性只作软约束

有了第一张被 compiler 接受的卡之后，对剩余 source 用简化 MMR：

```text
next_priority = 0.85 * priority - 0.15 * max_lexical_similarity_to_accepted_sources
```

相似度使用评分视图的 token Jaccard，空集合相似度按 0；这不等于语义重复。只在距离当前最高基础分不超过 0.10 的候选中使用多样性比较，避免为了新颖性选中明显较差的来源。参数必须进入评测记录。[R3]

只对**已接受证据对应的 source**计算重复惩罚：前一个候选返回 no_evidence，不应让同主题的有用来源被惩罚。没有第二种可靠内容就返回较少的卡，不强凑。

不同观点即使词面相近也不硬删；不使用“负面观点=低质量”“同观点=互相验证”等规则。跨 source 的 near-duplicate 暂不做不可逆合并，只软降权并记录重复线索。

## 7. Compiler：强化已经存在的规则，而非另写一个编译器

继续调用 `compile_evidence()`，保持一条原始 snippet → 0/1 卡，以及单次模型调用、引文 8–400 字符、连续原文、Python code-point 索引的约束。[C1 A7/A9]

加入成对反例：

```text
片段：测试框架五分钟上手，是回归测试首选。
问题：怎样判断工具调用参数正确？
期望：no_evidence；没有直接检查步骤或判据。

同一片段
问题：作者推荐了什么测试资源？
期望：可以归因转述为未验证的资源说法，不背书宣传。

片段：给工具传入固定样例，把实际参数与事先写好的期望值逐项比较。
问题：怎样判断工具调用参数正确？
期望：可形成 advice，引用真实连续原文。
```

提示词不会自动保证模型符合这些规则。单元测试里的 fake LLM 只能验证管道，不能证明真实模型能区分这三类情况；必须另做小规模真实编译评审。

不要对已接受卡靠关键词后处理删改 claim，更不要改 supporting_quote 凑 exact_match。编译器的版本固定值正被 TS 边界验证：仅提示词优化保持输出 schema 版本，另记录 prompt hash；若要升级正式版本，必须同步更新边界与测试。

## 8. 阶段 B：可选的一次 LLM 重排

阶段 A 仍然不能可靠理解同义表达、否定、隐含条件和营销话术。如果标注结果显示这是主要误差来源，再给最多 8 个候选做一次批量语义排序。[R4]

建议只让模型返回候选 ID 的完整排列及短的分项判断，不生成证据、URL、作者或事实确认状态。给模型的正文片段必须保留其原始窗口、位置和截断说明；实际 compiler 仍收到选中的原始 snippet。

限制：每请求最多新增 1 次 reranker 调用、固定输入体积上限、独立超时但共享 600 秒总期限；不得阻塞并绕过当前可终止的子进程机制。沿用现有 llm_client 配置，不换服务商，不要求购买新服务。

无效 ID、漏项、重复 ID、模型异常：不能伪装为 no_evidence。允许回到确定性排序，但必须报告已有 `rank_failed`/`stage=rank`，令该次为 partial；新增数字计数也要通过 Node 边界测试，失败响应的计数白名单需同步评估。

重排只是相关性判断，仍保留 `semantic_support_not_checked` 和 `unverified`。只有单独设计、验证了“引文支持主张”的校验流程后，才讨论改变语义校验状态；这不是本次 B 的工作。

## 9. 全文、缓存、追加搜索：暂不偷偷加入

已检查的 live 链路只实际使用 `search zhihu`。不能由此断言官方 CLI 永远不支持全文，也不能凭空写一个 `get_article` 调用。[C1 A14]

以后做正文能力探查时，先查看已安装 CLI/官方 Skill 的真实文档、权限与使用约定。只有得到明确支持，才能添加受控 enrichment，并独立升级 source_scope、引文定位、TS 边界和测试。否则如实保持 snippet-only；不绕过反爬、登录或付费限制。

本轮不接在线生产缓存。为可重复评测保存经过审查的本地候选快照是另一回事：必须标明抓取时间、版本、来源和非在线状态，不用于冒充新搜索。缓存未来需包括 query、参数、scope、TTL、抓取时间；编译缓存还需要 request/context/model/prompt/content hash，不能只按 URL。

## 10. 评测与上线条件

先固定同一批搜索结果，再离线比较旧排序与新排序，避免把搜索结果随时间变化误认为 ranker 提升。要比较 Query 改写时，另建实验，分开记录候选池，尽量在接近时间同预算运行。[R5][R6]

资料包给出 12 个评测问题及合成回归样例。真实评测建议至少覆盖 4 类需求，每类 3 题，先分为 8 题开发集和 4 题留出集。合成 fixtures 是工程测试，不是独立质量金标准。

重点指标（精确定义见 `EVALUATION_RUBRIC.md`）：
- 人工 Direct-answer Precision@3：前三个唯一来源中，能直接回答问题的比例；不足三个按空位记 0。
- Unsupported-claim rate：被接受卡中，人工判断包含引文不支持信息的比例。
- 返回卡片直接回答率 + question success@2：避免用“少返回卡”虚增精度。
- 冗余率、未覆盖子问题、调用次数、耗时、编译成功率和 no_evidence 原因。
- 凭据泄露、伪造 URL、原文被改写、schema 不兼容必须为 0。

建议推广门槛：开发集 Direct-answer P@3 比旧版至少 +0.10（绝对百分点差值），留出集不下降；如果基线 ≥0.90，则要求不下降且展示至少两例明确改进/冗余减少。所有门槛均为本项目拟定标准，不代表统计显著结论。样本不足就写“证据不足，继续实验”，不宣称全面更好。

保持 legacy 为默认；通过门槛后用户再选择启用 `v3`。撤回只需改一个本地配置，而非回滚整个 Server 集成。

## 11. 验收后能说什么

可以说：“在这组固定候选池和已标注问题上，V3 的指标是 X，相比旧版 Y；Windows Provider/HTTP 回归也通过。”

不能说：“因为本次返回 2 张卡，所以检索已优化”“精确引文说明观点为真”“多篇文章赞同就证明可靠”“正式 Roadmap 已完成”。

详细实施任务、函数边界、测试样例、Windows 命令及回退方式见 `CODEX_RETRIEVAL_OPTIMIZATION.md`。
