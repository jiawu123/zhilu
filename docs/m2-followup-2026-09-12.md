## Kyle 的五项收尾

### 1. 对齐首轮查询与补检索

最新 [PRD §6.3](../PRD-知乎知识驱动目标规划Agent-v0.3.md#63-query-planner) 要求首轮总计执行优先级最高的 2–3 个 Query，仅在关键路线、限制条件或反方证据不足时补充 1–3 个 Query。

当前 [Query Planner](../packages/zhihu/zhihu_m2/query_planner.py) 的 `jia-p0-baseline` 强制 3 个问题、每题 2 个 Query；[Provider](../apps/server/src/zhihu-provider.ts) 固定启用此 profile，[runner](../packages/zhihu/zhihu_m2/research_runner.py) 执行请求中的全部 Query。旧接入规格的 3×2 与最新 PRD 冲突，不能把两者都算验收完成。

验收：简单目标不强行凑题；首轮执行总数为 2–3；覆盖充分时停止；缺口明确时补 1–3 个 Query，并记录补检索原因及实际调用数。Kyle 提供规划/覆盖判断，Jia 对齐 Controller 的请求预算和调度。

### 2. 替换生产固定权重和逐篇编译

当前 runner 仍调用 [ranker.py](../packages/zhihu/zhihu_m2/ranker.py) 的固定加权公式，其中行动性、具体性词表偏编程领域；随后逐候选调用 [evidence_compiler.py](../packages/zhihu/zhihu_m2/evidence_compiler.py)。这不符合 [PRD §6.5](../PRD-知乎知识驱动目标规划Agent-v0.3.md#65-分层筛选不使用固定权重) 的硬过滤、模型批量分级、多样性选择。

验收：生产路径移除未经评测的固定权重排序；基础过滤后的候选批量判断相关性、用户适用性、支撑程度和时效风险；保留来源与引文校验。至少用编程及一个非编程目标验证，不增加 Embedding 或向量数据库。

### 3. 补足证据覆盖与真实分歧

当前 M2 只限制每题卡片上限；[runner](../packages/zhihu/zhihu_m2/research_runner.py) 返回 `routeCandidates: []`，[TS 边界](../apps/server/src/zhihu-boundary.ts) 也只接受空数组。M3 已能从证据提出路线，但结构不同不等于已验证语义分歧。

验收：覆盖充分时最终形成 6–8 张卡，落实同答案/作者数量限制，至少保留一条反例、限制条件或替代路线。选择一组存在真实分歧的来源，展示各路线的主张、适用条件、支持证据和风险；证据不足时报告缺口，不凑数、不编造第二条路线。Kyle 输出研究层候选与依据，Jia 同步 Contract/TS 边界并由 M3 生成最终可执行路线。

### 4. 接入 live Evidence Cache

当前 [research_runner.py](../packages/zhihu/zhihu_m2/research_runner.py) 明确没有缓存；现有 batch/replay 保存产物工具不是 live 请求自动复用的 Evidence Cache。

验收：实现本地证据缓存读写和明确的命中/失效规则；同目标、相关条件与研究问题重复请求时可复用证据，条件或时效要求变化时正确失效；保留来源、检索时间和风险标签。记录缓存命中及减少的实际搜索/模型调用数。职责对应 [知识模块分工](team-and-repo-plan.md#22-知乎知识模块负责人)。

### 5. 交付真实 Planner 与完整链路验收记录

已有真实 HTTP 记录使用预先给定的问题，Planner 调用为 0。当前检索、逐篇编译、跨问题请求均串行；Python 每题默认截止 600 秒，Node 单调用默认截止 630 秒。这些是错误保护上限，不是实际响应时间；当前记录没有可用于判断体验的分阶段耗时。

验收：与 Jia 在最终演示环境运行“确认目标 → 真实 Planner → 按需查询 → EvidencePack → M3 → 路线预览 → 用户确认”；记录环境、run ID、问题/查询/卡片数量、调用次数、总耗时及各阶段耗时。分别报告冷运行与缓存命中运行；超时、无证据、部分失败分别验证并明确标注真实或离线测试。单次 smoke 不作为稳定性或 P95 的证明。
