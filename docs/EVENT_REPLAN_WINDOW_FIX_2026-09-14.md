# 局部重排的同周依赖与无变化结果

用户截图中的错误是 `依赖排期冲突：t2 必须在 t1 结束后开始`。读取当前项目确认：正式版本为 3，每周 40 小时，t1/t2 均在同一周窗口，各预计 2 小时，t2 硬依赖 t1。

## 原因

M3 把任务起止日期作为周内可执行窗口，允许先完成 t1 再在同周完成 t2，并由 Plan Engine 检查硬依赖状态。M4 独自使用严格结束日早于开始日检查，因此会拒绝原本合法、且没有改变的同周安排。修正这一点后，40→40 无日期变化还会被旧“不得生成空 Patch”异常拒绝。

## 修改

- 从原 live/model 计划识别既有同窗 task→task 边，起止日期须完全相同、窗口至多七天。输入显式标示窗口语义；模型无权通过新日期创建该例外。
- 已标记的边可以保留/共同移动到相同短窗口，或改成严格先后日期。普通依赖、部分重叠、反向关系、长于七天的重叠和非任务依赖仍严格检查。
- 日期锁定限制是否可移动，不将已有周窗口变成连续占用。固定节点不可移动，预算仍包括所有任务及复盘。添加依赖环和硬依赖状态预检，避免同窗或无变化分支绕过执行顺序。
- 通过全部检查后，无实际变化返回 HTTP 200 `unchanged`，不保存空变更或改写 pending/正式计划/历史。仅预算变化保留正常 202 待确认流程。无变化也先检查版本，避免接受已过期结果。
- 界面保留原预演、显示“当前排期已满足约束，无需调整”，并禁用此次无效确认。实际变更和失败保持原有行为。

## 验证

Runtime 与 HTTP 回归先失败后通过，覆盖同窗保留/移动、锁定、固定/普通边界、超预算、循环与已开始的硬依赖状态、无变化和并发版本变化。后端、Runtime、Plan Engine 共 489 项通过，2 项平台限制跳过。

Web 共 59 项通过，包含 6 项无变化响应与界面回归；各工作区类型检查和 Web 构建通过。

使用当前真实项目进行只读编译诊断：9/30 小时可保留原日期，只需变更预算；40 小时无需变更。此步骤使用合成的“保留原日期”模型输出，只验证检查器。

随后重启后端，并对截图对应的 40→40 待确认事件调用真实 `/diff/replan`：1 次模型调用、0 次知乎搜索，约 1.882 秒返回 HTTP 200、`unchanged: true`。比较请求前后数据，正式计划、历史、全部 pending 均完全相同。健康检查正常，服务错误日志为空。

该修复不改变原路线的内容、引用或任务工时，也不表示此前的路线生成质量问题已解决。私人验证材料存于 Git 忽略的 `data/verification/event-window-CUuG9J/`。
