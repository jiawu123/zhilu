# 部分证据的采纳与逐卡容错

## 原因与范围

实际项目的历史草稿有 8 张已接纳的知乎卡，但 16 个任务都未引用任何卡。整体覆盖被标为 `insufficient` 后，旧编译器允许所有引用为空，使“路线依据必须用于任务”的检查被空数组绕过。

另一次 M2 `compilation_failed` 没有保存原始模型响应，无法断定是语义筛选、JSON、截断还是传输问题。本次多卡容错处理可复现的格式偏差，不把未知错误一概降级为成功。原 M2 已接纳部分相关、条件适用和间接支持，不需笼统降低来源真实性要求。

## 修改

- M2 同一候选返回多卡时，最多独立检查前三张，每张仍调用原单卡严格校验器；合格卡保留，错误卡隔离。保持来源 ID、原文精确引用及来源/作者/总数上限。相同卡去重；有坏卡或超限时不保留依赖该候选的研究摘要，后续裁剪任一摘要引用也会弃用摘要。
- M3 将覆盖不足与零证据区分。只要存在已接纳知乎卡，每条路线必须至少采用一条到具体任务；用户事实与 AI 推断 ID 不计入。其余卡和 AI 排期任务不强制引用。
- 每条路线输出 `evidenceApplications`，说明原主张如何影响指定任务的动作、产出或验收及适用条件。编译器验证完整的双向引用关系，不自动给任务补引用，不修改原卡片。采用说明保存为 `RoadmapperRun.evidenceApplications`，旧数据可缺省，新模型草稿必填。
- 用户已确认频率与投入不得为冲刺目标而擅自更改。个人经验、例子和缺数据建议应先试验、按结果调整，不能直接转为硬性验收。
- 每周输入直接提供扣除复盘后的 `maxTaskHours`，超额反馈也列出这一上限；未扩大原预算或弹性额度，最后的不足一周仍折算容量。
- 页面并列展示原证据、模型采用说明和对应任务；无直接知乎依据的 AI 任务单独标注待验证。已有卡时不会再提示完全没有原帖。
- 保留最多一次 M3 结构纠错与原计划校验，未增加 M2 自动重试或额外模型评审。最终采用仍经用户确认。

## 离线验证

先观察多卡容错、引用门槛/说明、页面展示和已知来源 ID 兼容性的回归测试失败，再实现并检查通过。

- Python 全套：1071 通过，1 项 Windows 不适用的 POSIX 权限测试跳过。
- 后端及 Runtime/Plan Engine：最终 476 通过，2 项平台限制跳过，包含带冒号的原来源 ID 和扣除复盘后的工时上限回归。
- Web：53 项通过；所有工作区类型检查通过，Web 构建通过。

## 真实回放与限制

仅复用已保存的真实研究快照，不新增知乎搜索。第一轮真实 M3 经过一次纠错后结构通过：19 个任务，14 个引用知乎，5 条采用说明。独立语义抽查仍发现发布频率偏离已确认节奏、饭点经验被写成硬性验收，因此没有将这一轮替换为用户待确认草稿。随后加强对应提示再验证。

第二轮两次模型响应均因末周工时超额被拒绝；抽查发现频率与采用说明任务列表也未完全一致。增加明确的任务工时上限后，针对已审阅草稿再做一次诊断纠错，仍因任务不在所属里程碑范围被拒绝，且存在缺周与频率问题。诊断合计 5 次真实模型调用、0 次知乎搜索；每次生产生成仍最多两次模型调用，没有增加自动重试次数。三个本地诊断目录分别为 `data/verification/evidence-usage-1OoBtf/`、`evidence-usage-5Ty3lX/`、`evidence-usage-SshsTW/`，均为 Git 忽略的私人材料。

因此本次完成的是逐卡容错、已有证据采纳门槛、可审查的采用说明和错误拦截，**不能宣称真实模型自动规划已稳定或整个报错链已解决**。原待确认草稿仍是旧结果，本轮没有覆盖它，也没有修改正式计划或历史。后端已加载新代码；重新生成将走新规则，模型输出不满足约束仍会失败。

采用说明是模型推断，结构校验不能保证语义相关或事实已经核实。即便离线检查及个案回放通过，也不代表未来模型输出有稳定成功率保证。M2 的网络、截断和整体非法 JSON 仍可能失败，失败不会被伪装成证据充足。
