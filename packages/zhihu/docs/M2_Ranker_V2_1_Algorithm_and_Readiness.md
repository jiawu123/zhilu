# M2 Ranker V2.1：打分算法说明与阶段评估

**项目：** 知乎知识检索与证据编译（M2）  
**代码版本：** V2.1，推广识别修补版  
**文档日期：** 2026-09-09  
**文档性质：** 对已有代码的说明与审核，不是新实现方案  
**阶段结论：** 可以进入同一工程学习场景下的 LLM Evidence Compiler 原型联调；不能据此宣称通用排序质量、自动事实核验或生产验收已经完成。

> Ranker 的任务是决定“先阅读哪些搜索材料”，不是判断“哪篇文章一定正确”。所有分数都是人为规则产生的优先级信号，不是概率、可信度百分比或经过校准的质量标签。

## 1. 这份文档依据什么

本说明对照了本次提供的 `zhihu_m2/ranker.py`、`tests/test_ranker.py`，以及用户贴出的五条 V2.1 排序结果。接口文本范围另外核对了用户上传的 `zhihu-cli-skill-0.5.3-beta.20260904115023.zip`。[S1][S2][S3]

当前五条输出只包含标题、点赞数和部分四舍五入后的分数，没有附本次完整搜索响应。因此，下文对这些结果的评估是“观察到的行为与规则是否一致”，不是在相同原始数据上重新计算全部精确分数，也不是重新阅读全文后的人工质量标注。[S4]

审核中没有访问知乎账号、使用 Access Secret 或调用 LLM。提供的 Ranker 源代码没有被修改。

### 1.1 最容易误解的数据边界

上传的 Skill 在 `zhihu/SKILL.md` 第 83 行明确说明：

> 优先使用返回的 `Title`、`AuthorName`、`ContentText` 和 `Url`。搜索摘要不是完整原文。

`zhihu/references/http-api.md` 第 142 行把 `ContentText` 定义为“内容摘要”，并说明高亮部分可能含有 `<em>` 标签。[S3]

所以，代码中的 `result.content_text` 应称为**返回的搜索摘要**，不能保证是完整回答。推广风险为零，最多表示这段可见摘要没有触发规则，不能证明原文章没有推广。

## 2. 当前模块在 M2 中的位置

```text
用户目标经过 Query Planner 转成检索 query
                    ↓
知乎搜索 → normalize_results() → list[ZhihuResult]
                    ↓
               当前 Ranker
                    ↓
       按候选阅读优先级排序的新列表
                    ↓
      精确去重、候选预算与来源多样性选择
                    ↓
      LLM 结合目标和背景提取 Evidence Cards
```

图中 Ranker 之后的步骤是下游职责，并非 `ranker.py` 已经实现的能力。去重代码此前已提供，但本次没有验证它是否已经在用户本机接入；LLM 编译也不在本次运行范围内。

### 2.1 输入与输出

| 输入 | 本模块中的用途 | 重要前提 |
|---|---|---|
| `query` | 字面相关性比较 | 当前检索问题，不等于完整的用户目标和背景 |
| `title` | 标题词元覆盖率和完整 query 匹配 | 标题可能与摘要实际内容不一致 |
| `content_text` | 推广识别；生成临时评分文本 | 是搜索摘要，原始内容不应被覆盖 |
| `vote_up_count` | 互动分的一部分 | 需要可计算的数值；负数按零处理 |
| `comment_count` | 互动分的一部分 | 评论数量不是评论质量 |
| `edit_time` | 编辑时间分 | 按 Unix 秒使用；缺失或零走默认分 |
| `now_ts` | 可选的评分时间 | 固定它可以复现相同的时间计算 |

`content_id`、`url` 和作者字段应继续保留给去重、归因和来源检查，但当前总分公式并不直接使用它们。`authority_level`、`author_badge_text` 和知乎原始 `ranking_score` 也没有参与当前总分。[S1]

接口保持不变：

```python
score = evidence_score(result, query, now_ts=None)
ranked = rank_results(results, query, now_ts=None)
```

`rank_results()` 返回一个新列表，列表元素仍是原来的 `ZhihuResult` 对象。它不是对象的深拷贝，也不会自动生成 Evidence Card。

### 2.2 当前输入校验的边界

本模块假设文本字段可作为字符串使用，互动字段可进行数值计算，编辑时间是秒级时间戳。它不是完整的 schema 校验器。例如，`vote_up_count=None`、毫秒级时间戳、正文不是字符串等输入，并没有被本模块统一转换或校验。

上游如果仅用字典 `.get()` 设置缺失字段的默认值，并不意味着已经处理了字段存在但值为 `None` 或类型错误的情况。这是之后的输入健壮性工作，不应误写成 Ranker 已完成的功能。

## 3. 总分公式

先给六个维度命名：

| 符号 | 函数 | 实际衡量的信号 | 在基础分中的权重 |
|---|---|---|---:|
| R | `relevance_score()` | query 与标题、摘要的字面重合 | 30% |
| A | `actionability_score()` | 步骤词、动作词和产出物词 | 25% |
| S | `specificity_score()` | 工程术语与数字、章节结构细节 | 20% |
| T | `recency_score()` | 距离编辑时间有多久 | 15% |
| E | `engagement_score()` | 点赞数和评论数的压缩值 | 10% |
| P | `promotion_score()` | 可见摘要中的推广组合信号 | 不加分，在最后施加惩罚 |

对符合输入约定的数据，各维度和最终分数都在 0 到 1 之间。

基础分：

```text
B = 0.30 × R + 0.25 × A + 0.20 × S + 0.15 × T + 0.10 × E
```

推广折扣和最终分：

```text
multiplier = 1 − 0.50 × P
F = max(0, min(B × multiplier, 1))
```

这正是当前 `evidence_score()` 的实现。[S1]

### 3.1 怎样理解推广折扣

| P | 保留基础分的比例 | 相对基础分扣除的比例 |
|---:|---:|---:|
| 0.00 | 100% | 0% |
| 0.23 | 88.5% | 11.5% |
| 0.70 | 65% | 35% |
| 0.75 | 62.5% | 37.5% |
| 1.00 | 50% | 50% |

这里的“35% 扣分”是乘法折扣。例如基础分 0.60、P=0.70 时，最终分是 `0.60 × 0.65 = 0.39`，不是直接减去 0.35。

P=0 不产生一个额外的“无广告奖励”；它只是让基础分不受这项惩罚。推广再强，也不会仅因这一乘法项把总分直接清零。不过，强推广文本还可能被排除出评分视图，间接降低 R、A、S，因此推广对结果的影响不只来自最后的乘法。

### 3.2 一次完整的示范计算

下面是专门用于解释公式的假想数值，不是本次五篇内容中的某一篇：

```text
R=0.60, A=0.80, S=0.75, T=1.00, E=0.30, P=0.40

B = 0.30×0.60 + 0.25×0.80 + 0.20×0.75 + 0.15×1.00 + 0.10×0.30
  = 0.18 + 0.20 + 0.15 + 0.15 + 0.03
  = 0.71

推广折扣 = 1 − 0.50×0.40 = 0.80
F = 0.71×0.80 = 0.568
显示为两位小数时：0.57
```

所有权重、词表和饱和阈值都是这一版的设计常数，没有根据人工标注数据训练或校准。它们不是研究证明的最优比例。

## 4. 推广风险 P：先识别局部组合，再汇总

### 4.1 拆成局部评分单元

`_paragraphs()` 保留了历史名称，但 V2.1 不只是按段落拆分。它按换行、中文句末标点、问号、感叹号和分号拆成局部单元：

```python
re.split(r"\n+|(?<=[。！？!?；;])", text)
```

空白单元被去掉。英文句号 `.` 不作为切分点，以减少 URL、版本号等被句号拆散的情况。这个规则也意味着英文长段落、只有逗号的混合句，仍可能没有被充分拆开。

### 4.2 检测四类词

| 类别 | 示例 | 作用 |
|---|---|---|
| 联系引导 | 加老师、加微信、扫码、私信、加V | 引导读者建立联系 |
| 获取或交易引导 | 领取、领资料、报名、购买、名额 | 引导读者采取领取、报名等行为 |
| 商业或资料对象 | 公开课、课程、资料包、训练营 | 表明正在谈论的对象 |
| 推荐表达 | 推荐、可以先听、听一下、可以参加 | 帮助保留弱推荐信号 |

完整词表见附录 A。“微信”单独出现已经不再被视为联系引导；`加V`、`加 v`、`加vx` 另外使用正则识别。

### 4.3 单个单元的分数 sᵢ

代码先检查有限的否定或提醒模式，再按照下表顺序判断：

| 条件 | 单元分数 |
|---|---:|
| 命中明确提醒模式，如“不要加老师……” | 0.00，立即返回 |
| 联系引导，并同时存在获取引导或商业对象 | 1.00 |
| 商业对象，并同时存在获取引导 | 0.85 |
| 商业对象，并同时存在推荐表达 | 0.35 |
| 其他情况 | 0.00 |

例如：

```text
“这门课程介绍 Python 的函数。”           → 0.00
“可以先听一下大模型应用开发公开课。”      → 0.35
“免费领取资源包。”                       → 0.85
“加老师免费领取内部资源包。”             → 1.00
“调用微信 API，并验证签名。”              → 0.00
```

0.35 是“存在推荐表达”的弱信号，不能解释为已经确认它是广告。单独出现联系词也未必形成信号。

否定保护只覆盖当前正则列出的表达，不是通用的否定理解。特别地，“不要错过名额”和“不要把它当成广告”不是通用免责条件。如果提醒和真实推广混在同一个未切开的单元里，当前提前返回零的策略仍可能漏报。[S1]

### 4.4 汇总成摘要推广风险

设每个单元的分数为 `sᵢ`，其字符长度为 `Lᵢ`：

```text
M = 最大单元分数
D = Σ(Lᵢ × sᵢ) / ΣLᵢ
H = 分数 ≥ 0.80 的单元数量
Q = min(H / 4, 1)

P = clip(0.65 × M + 0.20 × D + 0.15 × Q, 0, 1)
```

M 表示最强信号；D 是按字符长度加权的信号密度；Q 表示强推广单元的重复程度。D 不是“确定为广告的字符占比”，因为每个字符所在单元还乘了一个启发式风险值。

当前最强单元的权重是 65%，所以这不是一个单纯按“广告占了多少篇幅”计算的算法。即使很长的技术材料只夹了一句强引导，最高信号仍可能带来较明显的惩罚。这是当前偏谨慎的设计选择，不是已经证明最适当的惩罚强度。

在本次离线合成样例中：

```text
整段摘要只有一条弱课程推荐：
M=0.35，D=0.35，H=0
P=0.65×0.35+0.20×0.35=0.2975

整段摘要只有一条强联系与领取引导：
M=1，D=1，H=1，Q=0.25
P=0.65+0.20+0.15×0.25=0.8875
```

同一句弱推荐放进较长的普通内容中，D 会变小，因此文章层面的 P 可以接近 0.23。这个现象与当前第二篇结果一致，但仅凭 P=0.23 不能反推它究竟命中了哪一句；那需要保留局部诊断数据。

## 5. `clean_content()`：评分视图，不是删除原始证据

当前清理阈值为：

```python
STRONG_PROMOTION_THRESHOLD = 0.80
```

只保留单元分数小于 0.80 的文本，并用换行重新连接。局部单元分数 0.85 和 1.00 的内容会从评分视图排除；0.35 的弱推荐仍被保留。

注意：0.80 判断的是**局部单元分数**，不是整篇摘要的 P。不能拿 P=0.70 推断“没有任何句子会被清理”。

例如：

```text
原始摘要：
第一步调用 LLM API。加老师免费领取内部资源包。第二步实现工具调用。

评分视图：
第一步调用 LLM API。
第二步实现工具调用。
```

原始 `result.content_text` 不被修改。R 的摘要部分、A 和 S 使用评分视图；P 仍使用原始摘要；标题没有经过同样的推广清理。

这不是 HTML 清洗器，也不是提示注入防御模块。代码没有因此保证消除了恶意指令、所有营销内容、引用中的广告或者 HTML 高亮标记。LLM 编译阶段必须把原始摘要视为资料，而不是新的系统指令。

## 6. 字面相关性 R

### 6.1 分词规则

`_tokenize()` 把文本转成小写，然后做两种提取：

```python
# 英文、数字及允许的连接字符
r"[a-z0-9][a-z0-9_+.#-]*"

# 中文连续片段
r"[\u4e00-\u9fff]+"
```

英文部分提取词元；中文片段长度不超过两个字时保留，超过两个字时提取相邻两个字。结果放在 `set` 中，因此重复出现同一词元不会反复增加覆盖率。

```text
query：Agent Engineer 学习路线
词元：agent、engineer、学习、习路、路线
```

这不是中文语义分词，也没有翻译、词干归一、同义词映射、Embedding 或 LLM 判断。

### 6.2 覆盖率与完整 query 加分

```text
title_overlap   = query 词元中也出现在标题里的数量 / query 词元数量
content_overlap = query 词元中也出现在评分视图里的数量 / query 词元数量
```

将 query、标题和评分视图转为小写并去掉空白后，完整 query 如果出现在标题中，加 0.20；否则如果出现在评分视图中，加 0.10。两项不叠加。

```text
R = min(0.55 × title_overlap + 0.45 × content_overlap + phrase_bonus, 1)
```

query 不能产生词元时，R 返回零。

### 6.3 如何解释当前技术教程的 0.20

当前规则不会自动把 `Engineer` 与“工程师”、把“学习路线”与“从零到一系列教程”视为等价。技术教程因措辞不同得到较低 R，是字面匹配的局限，不足以判定其真实语义相关性低。

另一方面，标题可以匹配得很高，但正文实际未回答问题。后续 LLM 还需要判断“这条材料是否支持当前用户需要的主张”。不要把 R 当成这一判断的替代品。

## 7. 可行动性 A

在 `clean_content()` 的结果中，分别统计三组词表命中了多少个词表条目：

```text
sequence_score    = min(步骤词命中数 / 3, 1)
action_score      = min(动作词命中数 / 5, 1)
deliverable_score = min(产出物词命中数 / 5, 1)

A = 0.35 × sequence_score
  + 0.40 × action_score
  + 0.25 × deliverable_score
```

例如，步骤词有“第一步、然后、最后”；动作词有“调用、实现、测试”；产出物词有“API、工具调用、代码、日志”。完整词表见附录 A。

每个词表条目在一份文本中最多计一次，不按该词出现十次就加十次分。但同一个词可以同时属于多组，例如“测试”会影响动作项、产出物项和具体性项。当前算法也没有验证“动作和产出物是否在同一句形成了可执行步骤”。

因此 A 适合表示表面上的行动线索，不能保证步骤完整、正确、顺序合理或适合初学者。只出现步骤词也可以产生部分分数。

## 8. 具体性 S

当前 `specificity_score()` 明确偏向软件与 Agent 工程内容，不是通用领域的知识深度评估。

技术词分：

```text
technical_score = min(技术词表命中数 / 6, 1)
```

细节分：

```python
# 匹配数字的正则
r"\b\d+(?:\.\d+)?\b"

# 匹配章节或步骤结构的正则
r"(?:第[一二三四五六七八九十\d]+[步章节]|part\s*\d+|step\s*\d+)"
```

```text
detail_score = min((数字匹配次数 + 结构匹配次数) / 6, 1)
S = 0.75 × technical_score + 0.25 × detail_score
```

技术词例如 Python、API、JSON、LLM、tool calling、Agent Loop、evaluation。数字与结构按匹配次数计算，不是对这些数字的含义或真实性进行验证；某个编号也可能影响不止一项计数。

S=1 表示当前词表与细节计分已经达到上限，不是“专业程度满分”。术语堆砌、无关数字和模板化章节都可能把分数抬高。

词表匹配使用子串包含判断，不是严格的英文整词匹配，因此也可能出现偶然匹配。把这一版直接用于摄影、搬家、语言学习等任务，会产生不必要的软件工程词汇偏好。

## 9. 编辑时间分 T

当 `edit_time` 缺失或为零时，返回 0.50。否则：

```text
now_ts 未传入时，取当前系统时间的秒级时间戳
age_seconds = max(now_ts − edit_time, 0)
age_days = age_seconds / 86400
```

| 距离编辑时间 | T |
|---|---:|
| 不超过 180 天 | 1.00 |
| 超过 180 天，不超过 365 天 | 0.85 |
| 超过 365 天，不超过 730 天 | 0.70 |
| 超过 730 天，不超过 1095 天 | 0.55 |
| 超过 1095 天 | 0.40 |
| 时间缺失或零 | 0.50 |

这里只知道编辑时间，不能确认正文真的更新了知识。经典基础内容也未必因编辑日期旧而失去价值。

当前代码会把未来时间戳的年龄截为零，因此给 T=1；不会把未来日期识别为异常。这一点在本次合成探针中得到确认。若上游误传毫秒时间戳，也可能因此被误当成很新。

为了复现实验，建议对同一批数据传入固定 `now_ts`，而不是在不同日期拿时间变化后的总分直接比较。

## 10. 互动分 E

首先把负数点赞、评论按零处理：

```text
votes = max(vote_up_count, 0)
comments = max(comment_count, 0)
```

接着用对数压缩数量差异，并设置上限：

```text
vote_score    = min(ln(1 + votes) / ln(501), 1)
comment_score = min(ln(1 + comments) / ln(101), 1)

E = 0.75 × vote_score + 0.25 × comment_score
```

代码里的 `math.log1p(x)` 对应 `ln(1+x)`。在这里可以理解成：数量增加仍能加分，但增加同样数量时，高计数区间带来的分数变化不会和低计数区间一样大。

点赞达到 500 时，该子项封顶；评论达到 100 时，其子项封顶。E 只占基础分的 10%，所以在推广折扣之前，点赞最多贡献基础分的 0.075，评论最多贡献 0.025。

当前没有检查评论内容、互动来源、点赞异常或用户反馈质量。E 只能视为平台互动信号，不能视为真实性证据。

## 11. 排序行为

`rank_results()` 的核心是：

```python
sorted(
    results,
    key=lambda result: evidence_score(result, query, now_ts=now_ts),
    reverse=True,
)
```

使用未四舍五入的总分降序排序；打印时的 `round(..., 2)` 只改变显示。显示分数相同，不代表内部精确分数相同。精确总分相同时保留原有输入顺序。

Ranker 不会执行精确去重、限制作者数、自动剔除低分结果或改变原始列表的顺序。这些属于下游候选选择规则。若启用候选数量限制，应该保留未入选材料及其来源信息，而不是把它们认定为没有价值。

### 13.2 额外合成诊断：R=0 仍可得到 0.70

保持现有代码不变，构造了一段术语、动作、结构都充分的工程文本，给予饱和互动值和新编辑时间，查询却设为“番茄种植”。实际输出：

```text

```

公式本身也能直接推出：

```text
0.30×0 + 0.25×1 + 0.20×1 + 0.15×1 + 0.10×1 = 0.70
```

这是证明模型边界的合成样例，不是知乎真实结果，也不是额外一个已经修复的测试。它说明**当前没有“必须与目标相关”的硬约束**。因此，总分不能单独决定某条知识能否成为 Evidence Card。

### 13.3 额外合成诊断：空内容不会自动归零

正文和标题为空，互动为零、编辑时间缺失时，实际总分为：

```text
0.15 × 0.50 = 0.075
```

原因是缺失时间仍有默认 T=0.50。当前测试验证了空内容分数有界，没有要求总分必须为零。下游必须另做“是否有可引用材料”的检查，而不能只依赖总分。

### 13.4 其他已知局限

字面相关性不理解同义改写和跨语言表达；工程词表不适合不加修改地用于其他领域；术语和数字可以堆砌；编辑时间不是知识更新时间；推广规则不能理解所有否定、引用与反讽；摘要长度和截取范围也会影响分数。

现有五条输出没有人工相关性与证据质量标签，因此无法据此计算排序准确率、召回率或“提升了多少”。22 个测试通过也不等于这些经验有效性问题得到解决。

## 14. 是否可以进入下一步

**结论：可以，但下一步是带边界的原型联调，不是把 Ranker 当作最终质量裁判。**

| 使用方式 | 本次结论 | 原因 |
|---|---|---|
| 同一 Agent 工程学习场景内，给少量搜索候选排序 | 可以继续 | 接口清晰，现有规则用例通过，本轮输出可解释 |
| 用当前分数优先安排 LLM 阅读 | 可以继续 | 允许下游纠正字面匹配和表面细节误判 |
| 仅凭 F 或 R 的阈值删除所有低分材料 | 不建议 | 跨语言相关性低估、R=0 仍可高分等问题未解决 |
| 仅凭 F 给出“可信度百分比”或已验证标签 | 不可以 | 没有概率校准或事实核验 |
| 宣称已适用于所有类型的用户目标 | 不可以 | 当前具体性词表偏工程场景 |
| 认定整个用户项目已经通过测试 | 尚未验证 | 本次只跑了隔离环境的 Ranker 测试 |

没有必要继续为了这五条内容调权重、追求某篇固定排名第一。下一阶段应补上当前确实缺少的“结合目标理解材料”能力。

## 15. 下一阶段的边界与建议契约（尚未实现）

下一阶段为 **LLM Evidence Compiler**。先给它足够的上下文：当前研究问题、用户目标与背景、候选原始摘要、来源标识与 URL，以及 Ranker 的各维度分数。不要只给总分，也不要只给清理后的文本。

### 15.1 进入编译前的候选处理

保留 `content_text` 和 `url`；对真正重复的 `content_type + content_id` 做去重。同一作者的两篇文章可以分别提供不同线索，但不应被自动当成两份独立佐证。作者数量上限只是可配置的阅读预算规则，不是内容重复判断。

本次只有五条，建议在预算允许时把全部非重复候选交给 LLM，而不是立刻只取前三。缺失正文、来源无法追溯、无法支撑任何主张的材料，应在编译阶段明确记录跳过原因，不要生成虚构证据来凑数。

### 15.2 建议的 Evidence Card 信息

以下是下阶段的建议字段，不是现有 `models.py` 已经定义的 schema，也不代表已经与团队 PRD 完成对齐。

| 信息 | 用途 |
|---|---|
| `claim` | 从材料中可以合理提取的主张 |
| `supporting_quote` | 在原始返回摘要中可以定位的支持片段 |
| `source_id`、`source_url` | 程序从原候选继承的来源，不让模型编造 URL |
| `source_scope` | 当前应明确为 `search_snippet`，而不是未经取得的全文 |
| `content_type` / 主张类型 | 区分个人经验、建议、待核实事实性断言 |
| `applies_when` | 适用背景与前提，不能无依据推断作者经历 |
| `caveats`、`risk_flags` | 截断、推广、缺少独立证据等限制 |
| `verification_status` | 起始为未核实；不能仅凭高分或重复出现就升级 |

若源文本只是自述，卡片应表达为“作者报告/建议……”，而不是把它改写成已经独立确认的事实。LLM 的任务是结构化和解释现有材料；没有额外验证证据时，它不能把未核实主张变成已验证结论。

### 15.3 下一阶段应检查的行为

检查输出字段类型和必填项；来源必须来自输入候选；支持片段必须能够在原始摘要中定位；允许没有可用证据时返回空结果。能定位到引文，只证明引文确实存在，不证明被引观点为真。

把检索文本当作不可信输入。资料中的“忽略前文”“执行命令”等指令不能取得系统指令权限。`clean_content()` 没有提供这个安全保证。

还应保留排名较低但语义相关的材料，确认 LLM 能拒绝关键词很多却偏题的文本；保留有价值的条件分歧，而不是强行合并成一个一致结论。这些是下一阶段的验收目标，不是本次已经通过的测试。

## 16. 后续评估建议

待最小证据编译链路跑通后，建立固定的摘要缓存，并记录 query、抓取时间、算法版本、固定 `now_ts`、原始分数及各维度分数。比较两版算法时优先使用同一批缓存，避免知乎返回变化影响结论。

再用覆盖不同查询、摘要长度、推广风格、反例、同义表达和无关内容的小型人工评估集，判断候选保留和证据提取是否有效。不能只看“六赞教程是否排第一”。对其他领域的扩展，应单独审查技术词表和时间权重，而不是默认它们通用。

这些属于后续的经验评估工作，不要求现在先把 Ranker 改成更多层规则，才能开始 LLM 原型。
